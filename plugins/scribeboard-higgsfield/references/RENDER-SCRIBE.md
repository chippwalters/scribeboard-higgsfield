# /render-scribe: scored scene images through to the finished board video

Renders one image per Scribeboard scene (spec phase 6, `${CLAUDE_PLUGIN_ROOT}/scribeboard-spec.md`) and proves each one with a review score before it is used.

**The script is the pipeline.** `${CLAUDE_PLUGIN_ROOT}/scripts\render_scenes.py` owns every deterministic step: validation, prompts, engines, fallback, framing, upscaling, prompt stamping, scoring, iteration count, attempt selection, logging, and the final gate. Agents do only what a script cannot: render agents run one attempt, review agents look at the result and answer a checklist. No step depends on an agent remembering it, and the script refuses any command that is out of order.

## Roles

The same context never plays two roles for the same attempt. The script enforces renderer ≠ reviewer through the `--agent` / `reviewed_by` names, and writer ≠ voice reviewer through `narration.json` (legacy runs: `script.json`) `written_by`.

- **Orchestrator** (the conversation running this skill): writes a standalone `scenes.json` (a full run's `script.json` comes from the writer agent), runs `init`, reads `status`, dispatches agents, reads verdicts, runs `gate` and `report`, runs every `scribe.py` step (gate pages, board, video), applies the user's gate answers, and reports to the user. The user gates are Gate 0 (narration text), Gate 1 (script, images, title, character sheets), Gate 2 (the board image) and Gate 3 (the whole video). It **never renders, never reviews, and never edits** `state.json`, prompts, checklists, or images.
- **Render agent** (a sub-agent, one per scene attempt): follows `references/RENDER-AGENT.md`. Runs one `render` command and returns its result line.
- **Review agent** (a fresh sub-agent that rendered nothing in this round): follows `references/REVIEW-AGENT.md`. Runs `review-prep`, looks at the images, fills in the checklist, runs `verdict`.
- **Writer agent** (a sub-agent): follows `references/SCRIPT-WRITER.md`. Pass 1 writes `narration.json` (narration text only) from the source story in Chipp's voice (the Chippify profile) and names itself in `written_by`; it revises the flagged sentences after a failed voice review and rewrites the narration after Gate 0 edits. Pass 2 builds `script.json` from the approved narration, copying its sentences exactly.
- **Voice review agent** (a fresh sub-agent that did not write the text): follows `references/VOICE-REVIEW.md`. Runs `voice.py review-prep`, checks the narration (legacy runs: the script) against the profile and the source story, fills in the checklist, runs `voice.py verdict`.

Sub-agent types: in omp, render agents are `sonic` (mechanical) and writer, review and voice review agents are `task`; in Claude Code, `implementer` (render, writer) and `verifier` (review, voice review). Every brief is self-contained: paste the agent's reference file path, the absolute `--out` folder (or run folder), the scene number, and the agent's name.

## Engines (reused, never copied)

Machine paths and engine switches come from `settings.json` (neutral defaults) and `settings.local.json` (this machine, gitignored) at the repo root, read by `scripts/settings.py`; `$RS doctor` lists every value with the file it came from. The paths below are this machine's values.

- ChatGPT first: `codex_render.py` (Codex CLI, ChatGPT subscription), settings `render.drivers.chatgpt`, else from the /render registry `render.engine_registry`. Scene 1 by text; every other scene with scene 1's selected image as style reference (`edit --raw`). Two tries per attempt.
- Qwen-Image-2.1 only when ChatGPT fails twice, and only with settings `engines.qwen` true (here true; false = ChatGPT only: `validate`/`init`/`sync` refuse `"qwen"` and `"chatgpt+insert"` scenes and a twice-failed ChatGPT attempt simply fails): `comfy_render.py --variant qwen21` (`render.drivers.qwen_t2i`, else the registry: `render\engines\comfy\comfy_render.py`), text prompt only. `init --qwen-mode ref` switches scenes after scene 1 to `qwen21_edit.py` (`render.drivers.qwen_ref`, else the registry: `edit-image\engines\qwen21_edit.py`) with scene 1 as style reference; in the September 2026 samples that took 135 s against 55–67 s, did not carry over ChatGPT's bold marker look, and added a stray word, so text-only is the default. Qwen draws thinner, greyer lines than ChatGPT, so a fallback attempt usually fails review on style and the next attempt tries ChatGPT again. Runs under a 5090-share lease (settings `gpu_queue`; null = no lease, run directly).
- Upscaling: Real-ESRGAN in settings `realesrgan_dir` (`realesrgan-x4plus`, NVIDIA device picked explicitly) above 1.5x, Lanczos below, under a 5090-share lease.
- Prompt stamping: the /render skill's `prompt_meta.py` in settings `render.prompt_meta_dir`. Every raw and 4K image carries its prompt and a `.prompt.txt` sidecar.
- Narration audio: `scripts/narrate.py`, voice chosen by settings `narration.engine` (here `qwen-clone`; a fresh machine's default is `recorded`). `qwen-clone`: the Qwen3-TTS clone (`tts.qwen_*`, under a 5090-share lease). `elevenlabs`: ElevenLabs TTS with `tts.elevenlabs.voice_id`; `narrate.py clone-voice --sample <1-2 min of clean speech>` makes an Instant Voice Clone and prints the id. `openai`: OpenAI TTS preset voice `tts.openai.voice` (OpenAI's policy: tell viewers the voice is AI-generated). API keys only in the environment (`ELEVENLABS_API_KEY`, `OPENAI_API_KEY`), never in a settings file. `recorded`: the user reads `RUN/narration/reading.md` into one file `RUN/narration/recording.wav` (`.mp3`/`.m4a`/`.flac`); `narrate.py run` cuts it into sentences by faster-whisper word timestamps, and a sentence that fails is re-recorded alone as `RUN/narration/retake_<id>.wav`. Every engine checks each sentence with the same transcript check and writes the same `alignment.json`. How words are said: an optional `RUN/pronunciations.json` (`{"SQL": "sequel"}` or `{"SQL": {"say": "sequel", "heard": ["sequel"]}}`; whole-word, case-insensitive; keys starting with `_` are comments), merged over the user-wide file in settings `pronunciations` (the run file wins per word). The voice says the `say` form and the transcript check compares against it (counting each `heard` spelling as right); the script, gate pages and video keep the written form, and `recorded` runs list the entries in `reading.md` under "Say these words like this".

Style prompts come from `<styles_dir>\<style>\style_guide.md` (settings `styles_dir`, default `${CLAUDE_PLUGIN_ROOT}/styles`; the `image-prompt` block for scenes and character sheets, the `title-colour` block for the title card). Their colours come from the style's `palette.json` (`{role}` / `{role.cap}` / `{role.hex}` placeholders, `scripts/palette.py`), which also sets the board's flow-arrow colours; change colours only there. Launch styles: `rsa_animate`, `sketchnote`. **Choosing the style.** A run's style is the `style` field of its `script.json` (the writer copies the user's choice there; `narration.json` may carry it too before the script exists). `scribe.py status` uses that, else `--style STYLE` for a new run that names none, else `rsa_animate`. Once `scenes/state.json` exists, the style recorded there is the run's style for everything; if `script.json` later names another, `scribe.py` stops (stage `style`) until the user picks one (a different style means a new run folder, or `render_scenes.py init --reset`, which discards the scene images). It prints the style it uses (`style:` line) and passes it to `characters.py build` and `render_scenes.py init`. So when the user asks for a style, put it in the writer's brief (and in `script.json`), never only on the command line.

## Runbook

Run it top to bottom. Every stage ends in a command that must exit 0; a non-zero exit means STOP, read the `FAILED` message, and fix the cause.

Commands below use `$RS` = `$PY ${CLAUDE_PLUGIN_ROOT}/scripts/render_scenes.py`. Use forward slashes in every path passed to a shell (some agent shells strip backslashes), and tell every agent to run its commands in the foreground.

`render` reserves the attempt and hands the work to a detached worker process, then waits for it. The worker survives if the agent's turn ends early (omp moves long foreground commands to the background, and an agent that then ends its turn used to take the render down with it). `status` shows `rendering` while the worker's process is alive, and `render stalled` only when it is gone or has run for over 120 minutes; the next `render` records the stalled attempt as failed, and it counts toward the five.

### Stage 0: Preflight

`$RS doctor --style <style>`: every setting with the file it came from, every configured path, Codex login, ComfyUI at settings `comfy_host` (127.0.0.1:8188; only with `engines.qwen`), Real-ESRGAN, prompt stamping, the GPU queue, and the style guide. `narrate.py doctor` checks the selected narration engine only (its settings, its API key in the environment, faster-whisper, ffmpeg).

### Stage 1: Narration text, Gate 0, scenes

A full run approves the words before anything visual exists: narration text → voice review → Gate 0 → script → narration audio → scenes.

1. **Narration text (writer pass 1).** If the user gave prose, dispatch a **writer agent** with `references/SCRIPT-WRITER.md` (the source path, the run folder, its name, "pass 1"). It writes only `RUN/narration.json`: the story told in Chipp's voice from the Chippify profile (settings `voice_profile`, here `${CLAUDE_PLUGIN_ROOT}/profiles/narrator.md`) as paragraphs (one per scene to come, each with a short title) of sentences with ids `"P.S"`. Each sentence is exactly one sentence of 6 to 16 words, and spoken numbers are words. **Segment balance:** each sentence is one segment drawn by one pen at constant speed while it is spoken, so the writer sizes every sentence while writing (aim 8-14 words, `render_scenes.SEGMENT_TARGET_WORDS`; hard band 6-16, `SEGMENT_BALANCE_WORDS`), merging short beats into a neighbour and splitting long ones. No elements, layout hints or other visuals yet. `written_by` names the writer, and `voice.py validate-narration --run RUN` checks the file.
2. **Voice review** (before Gate 0): `scripts/voice.py` (D64) reviews `narration.json` (`script.json` in a legacy run that has no `narration.json`). Dispatch a fresh **voice review agent** with `references/VOICE-REVIEW.md` and a name that never wrote the text: `review-prep` and `verdict` refuse `written_by` and every earlier round's writer (ignoring case and whitespace). It checks nine global items (cadence, short beats, no hype, no AI polish, performable fillers, facts preserved, nothing invented, opening/sign-off as configured, spoken numbers as words) and every sentence, and `verdict` scores the checklist into `RUN/voice/voice.json`. Pass = every check holds and no sentence is flagged. A fail goes back to the writer agent, which applies every flagged sentence's fix: while any flagged sentence is unchanged (whitespace aside), `scribe.py` keeps routing to the writer, even if other edits made the review stale, and `review-prep` refuses the revision. The revision is reviewed in the next round. The third failed round in a row is `flagged`: the run continues and the Gate 0 narration question (Gate 1's script question in a legacy run) lists the flags. A revision that also changed unflagged sentences, the sentence ids or the source story is a new text and starts a fresh count. The review holds while its **fingerprint** holds: the sentences (whitespace-normalized), the voice config, the source story's sha256 and the profile's version. Changing any of them makes `voice.json` stale and needs a new review; `written_by`, titles, elements, layout hints, `title_text` and formatting (including whitespace inside sentences) do not.
3. **Gate 0** (`gate0.py build/apply --run RUN --round N [--alt LABEL=PATH ...]`): the narration text alone, no audio. `build` refuses unless the voice review passed or flagged this exact narration. The page names the source story, then asks one approve/edit question (with an optional note) per paragraph, showing its title and its sentences with their ids, then one for the whole narration, then the general notes. To offer alternatives, for example a shorter version the user asked for, pass each as `--alt LABEL=PATH` (a Markdown file of narration text). Every alternative is shown in full beside the current narration, and a required `version` question offers `current`, `alt:<LABEL>` or `merge` (described in the note). The alternatives are copied into the round folder and recorded with their sha256. `apply` writes `changes.json`. Any edit or another version goes to the writer agent (pass 1 revision) with the round's `changes.json` and, for a chosen alternative, its round-folder copy. The writer rewrites `narration.json`, which changes the fingerprint, so `scribe.py` asks for a new voice review and then round N+1. Gate 0 passes when the latest round's `approved_fingerprint` equals the current narration fingerprint.

   **After an approval, only the changes.** When an earlier round approved a narration and the writer has changed it since (for example after a Gate 1 note), the next round asks only about the paragraphs that differ from the approved text: a changed title, or any sentence added, removed or reworded (whitespace ignored), plus a new paragraph or one a later round asked to edit. Each such paragraph's body lists only its changed sentences, old and new. The unchanged paragraphs appear as one collapsed "approved in round R" entry in the intro and keep their approval; there is no whole-narration question (the voice flags and the word count move into the intro; the general notes stay). Approving every shown paragraph approves the narration. The approved text is the round folder's `narration.shown.json` (every build copies the shown `narration.json` there); rounds built before that use the voice round that reviewed it (`voice/r<K>/narration.json`). With no approval yet, or nothing changed paragraph by paragraph, the page is the full one above. A round that was built but not answered (no answers file, no `changes.json`) can be rebuilt in place with the same `build --round N`; its old page files are replaced, and `scribe.py` keeps waiting on that round.
4. **Script (writer pass 2).** Dispatch the writer agent with "pass 2". It builds `script.json` from the approved narration in the spec's `script.json` scene format (phase 3), one scene per paragraph (scene id = paragraph id). Its `segments` are the approved sentences with the same ids and the text copied exactly; `source` and `voice` are copied too. It adds each scene's `elements` (`id`, `desc`, optional `text` label of 1-5 words), its `layout_hint`, each segment's `reveals` (the element ids it introduces), `characters` and `title_text`. Each element is revealed by exactly one segment, and each segment gets a comparable amount of drawing sized to its sentence (segment balance: as a rule one main element per segment, never three big drawings in one segment and a small label in the next). A `layout_hint` places the groups in reading order but never asks for arrows or lines connecting them (D60: the segments are later cut apart and packed onto one board). `written_by` names the writer. Because the sentences are identical, the fingerprint is too, so the voice review still holds; `scribe.py` refuses a script whose sentences, `voice` or `source` differ from the approved narration ("rebuild script.json from the approved narration"). Example: `${CLAUDE_PLUGIN_ROOT}/samples\render-scribe-test\scenes.json`.

   A legacy run (`script.json`, no `narration.json`) has no Gate 0: the voice review checks `script.json` itself, after the script stage.
5. `$RS init --scenes <scenes.json> --style <style> --out <folder> [--alignment <RUN/alignment.json>]` validates the structural rules above (not the layout-hint wording, and not `written_by`, which `scribe.py` and `voice.py` require), writes the prompts, and creates `state.json`. Fix any validation error in `scenes.json` and run it again.
   - With `--alignment` (the full pipeline; narration from `scripts/narrate.py`), each scene's spoken length sets its **ink budget** at the style's constant drawing speed (`styles/<style>/module.json`): drawing time → ink length → `sparse` / `medium` / `dense`. The tier's wording and the scene's sentence count and length go into the prompt, and `RUN/budget.json` records it.
   - `$RS validate --scenes <file>` checks a script without writing anything.

In a full run, **don't pick stages by hand**: `python ${CLAUDE_PLUGIN_ROOT}/scripts/scribe.py status --run <RUN>` inspects the run folder and prints the one next step (narration text → voice review → Gate 0 → script → narration audio → character sheets → init/sync → this loop, including any rebox → contact sheet and run summary (`report`) → title card → Gate 1 → board image → Gate 2 → video and its per-scene excerpts → Gate 3). The file formats are in `${CLAUDE_PLUGIN_ROOT}/.orchestrator/contracts/run-folder.md`.

### Stage 2: Render ⇄ review loop

Repeat until `status` prints `ALL SCENES DONE`:

1. `$RS status --out <folder>` prints each scene's NEXT action. Do exactly what it says, nothing else.
2. For each scene whose NEXT is `render attempt N...`: dispatch a render agent. Scene 1 always goes alone first; it is the style reference and must pass (or be flagged) before any other scene renders. After that, dispatch every renderable scene's agent in parallel.
3. For each scene whose NEXT is `review attempt N`: dispatch a **fresh** review agent (it must not be any agent that rendered in this round). Several scenes' reviews may go to parallel review agents.
4. Read each agent's result line (`RENDER_JSON`, `VERDICT_JSON`, or `FAILED ...`). Do not open the images or re-judge them; the verdict is the judgment. If a render agent comes back without a line, run `status`: while it says `rendering`, the worker is still going; wait with one blocking command, never a polling loop, and dispatch nothing new for that scene.

The script decides what happens next: a pass selects that attempt; a fail makes the next render use the verdict's `requiredFix`; the 5th attempt without a pass selects and flags the best-scoring attempt. A scene reported as `exhausted` has no reviewable attempt at all; stop and tell the user.

### Stage 3: Gate and report

1. `$RS gate --out <folder>`: every scene has a selected attempt with a passing (or flagged) verdict for exactly that image, reviewed by a different agent than rendered it, with the 4K file at the exact scene size and its prompt sidecar.
2. `$RS report --out <folder> [--no-open]` re-runs the gate and writes `_contact.png` and `run_summary.md`. Without `--no-open` it also opens every `scene_N_4k.png` in the default image viewer. That is the pipeline's one deliberate window; use `--no-open` on unattended runs.
   In a full run `scribe.py status` routes this step itself (`report --no-open`) right after the image gate passes, when `_contact.png` is missing or older than a selected scene image, and only before the first Gate 1 round.

**Character sheets.** Characters declared in `script.json` (`characters`, contract v1.1) get a text-free multi-view sheet from `scripts/characters.py build --run RUN` before any scene renders. `render` refuses a scene that shows a character without a sheet. Every render of such a scene attaches the sheets (`--ref`); with no style reference yet, Image 1 is a blank canvas. The reviewer answers `characters[].matches_sheet`, and a mismatch costs 20 points and fails the attempt.

**Per-scene engine.** A scene may set `"engine"` in `script.json` (default `"auto"`: ChatGPT first, Qwen after two ChatGPT failures). The other values are used only on the user's decision, for content ChatGPT will not draw faithfully (for example a copyrighted character whose renders are blocked or silently replaced):
- `"qwen"`: every attempt renders with Qwen-Image-2.1 from the text prompt alone (no style reference, no character sheets attached), so expect thinner lines and a style deduction. Changing a scene's `engine` (or its `insert`) counts as a picture change, so `sync` starts a new round for it.
- `"chatgpt+insert"` with `"insert": {"character": "<declared id>", "where": ["<spot 1>", "<spot 2>"]}`: ChatGPT draws the scene and leaves those spots empty, then Qwen-Image-2.1 draws only that character into them. List one description per spot: Qwen fills one spot per call (run1 scene 13: asked for two spots at once it drew one, 4 of 4 times), so each spot gets its own pass on the previous pass's result; a plain string is one spot. ChatGPT's prompt (`prompts/scene_N.chatgpt.txt`) never names him: the elements drop his sheet name, every mention of his name anywhere in the prompt (descs, layout hint, `where`, a review fix) becomes "a gap of plain blank paper", his sheet is not attached, and a sentence built from the spots asks for plain blank paper there with nothing drawn: no person, outline, silhouette or placeholder shape (D76: wording that mentioned "the size of a figure" or "a character is added later" made ChatGPT draw empty silhouettes, and Qwen then put him in the wrong place). `validate` refuses a label that names him. So write the scene's element descs and layout hint around the empty spaces ("Obi-Wan ...; to his left, an empty white space about half as tall as Obi-Wan") and keep his id in those elements' `characters`. In the same 5090-share lease as the upscale, `qwen21_edit.py` edits ChatGPT's flattened image (`--megapixels 0 --keep-size`) with one reference, the top-left panel (front, full body) of `characters/<id>_sheet.png` cropped to its ink (`--ref-megapixels 0.5`), one seed per attempt, and the instructions in `prompts/scene_N.insert.txt` (one line per pass). Each pass's composite keeps every pixel except new ink: pixels white before the pass and ink in Qwen's output, grouped after a small close, in components large enough and mostly more than 4 px from the existing lines (Qwen's slightly shifted redraws of existing lines are dropped); Qwen's pixels are pasted inside those, grown 2 px, on white only. The attempt records `engine: chatgpt+qwen-insert`, `insert` (reference, seed, per-pass Qwen output and kept components, pasted pixels) and `insert_mask` (`attempts/scene_N_aK_insert_mask.png`, every pass); ChatGPT's prompt and every insert prompt are stamped. A pass that keeps no component (or whose new ink covers over a quarter of the picture) fails the attempt with the reason, and a ChatGPT failure fails it too (no Qwen fallback), so the loop retries. The reviewer gets his sheet (`characters[]`) and `insert` in `REVIEW_JSON`, and checks that he stands in every listed spot and matches his sheet. Setting or changing the insert changes the prompt, so `sync` starts a new round.

**Sentence groups and the density pass.** With narration timing, the prompt lists one group of drawings per sentence, each with its share of the scene's line work (the sentence's share of the drawing time; one pen runs the whole story, so there is no end hold and only the story's first sentence waits for the lead-in). After a review passes, `verdict` builds the segment masks and measures each segment's drawing time with `reveal.py`'s own stroke/fill analysis at the style's constant speed; erased connector arrows don't count. Each segment is compared with `density_band` (module.json, 75–125%) of its sentence's available time. With `density_mode: "warn"` (the default, D77) a segment outside the band is only recorded as `density_warnings` on the verdict and in `VERDICT_JSON`; the attempt still passes, and the board video absorbs the difference with `max_speedup` and short pauses. With `density_mode: "fail"` the attempt fails and a generated fix naming each off segment (simpler/smaller, or larger/more detailed) is added to the reviewer's fix for the next render. When five attempts fail, the kept attempt is chosen in two steps. An attempt whose checklist passed, so its density was measured, always beats one whose checklist failed (a missing element or wrong label never reaches the density pass). Among those, the best review score minus 100 points per unit of density outside the band wins. `$RS reflag --out <folder>` re-picks every flagged scene with the current rule (used after a ranking fix) and logs a `reflag` event per changed scene.

**Segment masks.** When a scene's attempt is selected (passed, or flagged after five), the script builds `scene_N_segments.json`, one mask per segment, one arrows mask, and one highlight image per segment plus `scene_N_arrows_highlight.png`, from the review agent's boxes. Connector arrows between groups are boxed on their own (`arrows`) and **erased** (D60): an ink blob mostly inside the arrow boxes (and more there than in any one element box) is arrow ink, and so is any other ink inside an arrow box and outside every element box; arrow ink is in no segment mask and is never drawn. Each other ink blob goes to the element box covering most of it; a blob equally inside nested boxes goes to the smallest, and a blob across boxes is split pixel by pixel (smaller boxes win). A blob that goes mostly to one box but also has real ink in the box of another segment's element, outside the winning box (at least 3% of the blob and 2000 4K px; a box that encloses the winning one does not count), is split pixel by pixel too (D83: a clipboard outline drawn touching the desk now stays with the clipboard). Ink touching no box joins the element or arrows whose ink is nearest, and only specks under 50 px stay `residual`. The gate refuses a scene whose masks are missing, stale, empty, or built without the arrows split. `$RS regions --out <folder> --scene N` rebuilds them.

**Rebox (D60).** A scene selected before arrows were boxed on their own keeps its image and score but needs new boxes: dispatch one fresh review agent per scene with the "Rebox" brief in `references/REVIEW-AGENT.md`. It runs `$RS rebox --out <folder> --scene N --agent <name>` (box sheet and `boxes.json`), measures element boxes without the connector arrows plus one box per arrow, then runs the same command with `--file <filled.json>`, which rebuilds the masks and highlights and logs a `rebox` event. `scribe.py status` names the scenes that still need it.

**Title card (D62).** The story's hand-lettered title is rendered and reviewed by `scripts/title.py` (its own render/review loop, style reference = scene 1); the title reviewer follows `references/TITLE-REVIEW.md`.

**Rounds (Gate 1 edits).** `$RS reopen --out <folder> --scene N --fix "<note>"` starts a new round for a scene: a fresh five attempts, with the note as the first render's fix. `$RS sync --out <folder> --scenes <script.json> --alignment <alignment.json>` re-reads the script after edits.
- A selected scene starts a new round only when its elements, layout hint, engine or insert changed (with a new prompt).
- If only its segments changed, it gets new masks.
- A prompt that changed only in wording or budget is stored for any later round.
- A scene without a selected image starts a new round whenever its prompt changed.

Report to the user: the output folder, the per-scene table from `run_summary.md` (status, attempts, scores, engines), every flagged scene with its best score and worst issue, and every Qwen fallback with its reason.

### Stage 4: Gate 1, board, Gate 2, video, Gate 3

`scribe.py status` prints each command in turn; don't pick them by hand. Every gate, Gate 0 (Stage 1) included, is an html-questions page: one self-contained HTML file in the round folder (`RUN/gates/gate<N>-r<R>/`) that links the run's own images, audio and video where they are (Gate 2 copies `board.png` and Gate 3 cuts its clips into the round folder). `build` opens it in a new tab of the user's Chrome; pass `--no-open` to skip that. Every page shows a rail across Gate 0-3 (`RUN/gates/gates.js`, one spot per gate, the newest round of each): grey = built and waiting, teal = answered with edits, orange = passed. The user pastes the copied JSON; write it to the gate's `expectedAnswers` path, then run `apply`, which sets the dot. A required question missing from the paste is refused: ask the user for it and never invent an answer. Rounds built before 2026-10-08 (older page format) still apply as before.

1. **Gate 1** (`gate1.py build/apply --round N`). The page asks about:
   - the title card;
   - the script and the narration (free-text notes);
   - the character sheets, when there are any;
   - per scene, its image, plus each segment's highlight.

   Each item is approve or edit, with an optional note. Approvals are tied to the approved image's sha256, so a re-rendered scene must be approved again.

   Applying edits: text goes to the writer agent. In a run with `narration.json`, a change to the spoken sentences is made in `narration.json` first (pass 1 revision), and it goes through the voice review and a new Gate 0 round again before pass 2 rebuilds `script.json` from it. Changes that leave the sentences alone (elements, layout hints, `title_text`) go straight into `script.json`. In a legacy run, a new voice review follows only if the spoken sentences change. Image notes go to `$RS reopen --out <folder> --scene N --fix "<note>"`. Then run `sync`, then write `RUN/gates/gate1-rN/edits_done.json` (`{"round": N, "actions": [...]}`). A title-only edit needs no `edits_done.json`. A note about how a word is said (for example "say SQL as sequel") becomes an entry in `RUN/pronunciations.json`, then `narrate.py run`: only sentences with that word are made again (`recorded`: re-cut from the existing recording and re-checked). When a sentence fails the transcript check again and again because a name is misheard, add the misheard spelling to that entry's `heard` instead of rewording the sentence.
2. **Board** (`stitch.py board --run RUN`). Every segment (arrow ink erased) plus the title is packed into one 16:9 board in story order (layout in `module.json` `layout`). Segments of one scene drawn on or inside each other in the scene image (their mask ink touches, or one's ink box lies mostly inside the other's; `layout.glue`) are glued into one rigid compound (D83): one shared scale and tilt, every member where the scene image has it, packed as one piece at its first member's place. Members still draw one by one with their own masks, reveal order, shots and camera, and no flow arrow joins two members. Then a few flow arrows fill the blank spots: only in a wide gap between two pieces that follow each other in the story (including the last piece of a scene → the first of the next), pointing to the later one; hand-drawn marker style (black, orange-red, teal; slight wobble; open or filled head), never touching ink, the widest gaps first (`layout.arrows`). They are board-level flow arrows; D60 still keeps connector arrows out of the scene images. Outputs: `videos/board.png` (3840×2160) and `videos/board_layout.json` (version 2: every placement, the compounds, every arrow, the fill numbers, and a fingerprint of the images, masks, title and layout values).
3. **Gate 2** (`gate2.py build/apply --round N`): one page, the board image (linked to open at full size) with its fill numbers, and one required question: approve, or edit with a note ("tighter", "new seed", "move scene 5 next to 6", "fewer arrows"). No video frame is rendered until the board is approved.
   - `gate2.py apply` only records the answer. You apply an edit in `module.json` `layout` (`seed`, `gap_px`, `margin_px`, `scale`, `tilt_deg`, `arrows.*`, `glue.*`), run `stitch.py board`, and the next round shows the new board.
   - The approval holds while the layout fingerprint is unchanged. A changed scene image, mask, title or layout value means a new board and a new round; the next round number is the highest existing one + 1. Camera values are not part of the layout, so a camera change never reopens Gate 2.
   - `drawing_speed_px_s` is tuned by hand, not at a gate; it also sets the scene budgets, so `scribe.py` then asks for `sync` first.
4. **Video** (`stitch.py build --run RUN`; `--preview` for 960×540). It renders from the approved `board_layout.json` and never packs again; it refuses a missing or stale layout.
   - **Shots (D82).** The camera does not move on every segment. The title is one shot; then each scene's segments are grouped into shots of 2 or 3 consecutive segments (`camera.shot_size`; 4 → 2+2, 5 → 3+2 or 2+3, 3 → 3, a one-segment scene alone). A shot never spans a scene change. Its window frames all of its pieces and the flow arrows between them, is at most `camera.max_shot_window_frac` of the board width (0.3: on run1's 20432 px board, about 6100 board px, so the drawings stay legible at 1080p), and among the valid splits the tightest framings win. A segment gets a shot of its own only when its scene cannot be split into 2-3 runs that all fit, and then in as few single shots as possible (run1: 8 of 57).
   - **The pen.** One pen runs the whole story. The title draws first in `title_draw_s` (3 s), and the narration starts `title_gap_s` later. Each segment starts at its sentence (the first adds `lead_in_s`), and no time is added between scenes. Inside a shot the next segment may start as soon as the previous one ends.
   - **Hold, rest, one glide.** The window holds still while a shot's segments draw in turn, rests `camera.dwell_s` (0.5 s) after the shot's last segment, then makes one glide to the next shot. The glide lasts `camera.move_s` (1 s), starts at max(draw end + `dwell_s`, next draw start − `move_s`/2), and eases in log width through a window over the two pieces either side of the cut (a gentle push-in or pull-out between shots of different sizes). The new shot's first segment may wait until mid-glide, so its first strokes are in frame. To make room for the rest, a segment may draw up to `max_speedup` (1.35×) faster. A pause is inserted only when a segment would start more than `segment_overlap_s` after its sentence.
   - **Flow arrows.** The pen draws each arrow in `camera.arrow_draw_s` (0.4 s), shaft then head. An arrow between two shots draws across the middle of the glide (where both segments are in frame) and the window widens if the whole arrow does not fit; an arrow between two segments of one shot draws right before the later segment, inside the held frame. Nothing pops in, and the arrows show in the final zoom-out.
   - **Framing.** The window is never narrower than 1920 × the largest piece scale on the board (`camera.min_window_w`), so nothing is upscaled. The video ends with a zoom-out to the whole board.
   - **Outputs.** `videos/final.mp4` (1920×1080) and `final_timeline.json` (v2, with its `shots`). The `Scene-NN.mp4` files are excerpts of `final.mp4`, each cut at min(the glide into the scene, its first sentence), which in practice falls in the gap between sentences.
5. **Gate 3** (`gate3.py`): the whole video and the board, then each scene on its own (a clip cut on the narration, so every sentence is whole; scene 1 includes the title, the last scene the zoom-out).
   - Camera notes ("too much motion", "hold longer", "frame tighter") go to `module.json` `camera` values (`shot_size`, `max_shot_window_frac`, `dwell_s`, `move_s`, `hold_pad`, ...) or, when no value covers them, to `stitch.py` itself; then `stitch.py build`. A camera change leaves the layout fingerprint alone, so the Gate 2 approval holds and the rebuilt video supersedes the open Gate 3 round. A layout edit (seed, gaps, arrows) goes back through `stitch.py board` and a new Gate 2 round before the video is rebuilt.
   - When the user approves the final video in chat instead of on the page, record that in `.orchestrator/state.md` and stop. Never fabricate a Gate 3 answer file.

Change only what an edit needs. A skill or code change never means rebuilding an approved run's video unless the user asks for it.

## Scoring (computed by the script)

Start at 100 and subtract:

| Finding | Points |
|---|---|
| Element missing | 20 (fails the attempt) |
| Label misspelled or missing | 20 (fails the attempt) |
| Hand, pen, or marker visible | 15 (fails the attempt) |
| Element cut off at the image edge | 15 (fails the attempt) |
| Frame or border; background not plain white; photographic or 3D look; gradients or grey wash | 15 each |
| Unrequested text | 10 each |
| Elements touching or overlapping | 10 |
| Layout hint not followed | 10 |
| Drawing style differs from the scene 1 reference | 10 |
| Character doesn't match its sheet | 20 each (fails the attempt) |
| Unrequested object | 5 each |

Pass = score ≥ 80 and no failing finding; with `density_mode: "fail"` also every segment inside the density band (the default `"warn"` only records misses). Colour is never scored.

## Rules

- Never skip a stage or a gate. Never run `render` or `verdict` yourself as the orchestrator.
- Never edit `state.json`, a checklist, a verdict, or an image by hand. If the loop looks wrong, fix the script, not the state.
- Never bypass the 5-attempt limit or re-review an attempt that already has a verdict.
- The Codex mirror `${CLAUDE_PLUGIN_ROOT}/.agents\skills\render-scribe\` is a verbatim copy of this folder; update both together.
- A different agent checks every piece of work (D64): renders and titles by a fresh review agent, the narration (legacy runs: the script) by a voice review agent, and every builder agent's code change by an independent reviewer before it is used on a run. A builder never reviews its own output, under any name.
- No console windows (D68): every `subprocess` call in `scripts/` passes `creationflags=NO_WINDOW` (`CREATE_NO_WINDOW`), and the WMI render worker starts with `ShowWindow=0`. New code follows the same rule: nothing the pipeline starts may open a window or take focus. The only exceptions deliberately open something for the user: `report` without `--no-open` opens the finished images, and a gate `build` without `--no-open` opens its page in a new Chrome tab.
